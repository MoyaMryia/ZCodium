这个仓库是什么

上游在 2026-09 被迫将 ZCode 客户端开源，但放出的源码与他们实际发布的安装包并不等价：发布包里有一批开源代码中没有的功能。

ZCodium 的做法是跟进上游官方仓库，同时把这些「只在发布包里存在」的功能以各种方式补全——补齐缺失的内置插件与技能、比对 i18n 键定位功能缺口、按协议与设置 schema 对齐交互链路——让自建的源码能够构建出与官方包能力对等的产物。

所有补全都记录在 .agents/specs/ 下的 spec 中，包含范围、状态所有者、接口契约与验收场景。

[嘘... 别让用户发现我们在干什么]
官方 3.14.0 之前的版本，会在每次提问前打包整个 workspace（含 .git），加密上传至对象存储——私钥在服务端手里。该行为已从上游移除，本仓库同样不实现，只在 repo-snapshot-parody 留了一份 localhost 复现用于审计对照：密钥本地生成、默认拒绝非回环目标。

与官方包的能力差异 · 截至 3.14.1

已补全

  • 内置插件与技能——安装包只分发源码资源完整且明确注册的插件，范围见对应 spec。
  • Computer Use 的模型可见面——scripts/computer-use-client.mjs、技能与文档。

528 个键。安装包里有的，开源源码里没有——这就是差距。

有意不补全

  • 仓库快照上传。打包 workspace、加密上传、服务端持钥——不实现，只留审计复现。
  • 官方遥测采集与上报。保留安全的本地诊断，默认无上报；用户可显式配置自己的 OTLP 接收端。

已定的补全路线

  • bots 走 AstrBot 插件，不逐个平台重写。四套平台适配交给开源的多平台机器人框架，ZCodium 只维护桥接契约——astrbot-zcodium-plugin。
  • Computer Use 通用化。按 Actuator 接口分层实现，broker / bridge 基础设施已齐备且本来就是通用的。
  • image-search 默认指向本地。http://127.0.0.1:8787——仓库内暂无本地搜图后端，需要自行部署。

与上游的关系

本仓库跟踪上游 zai-org/ZCode。上游更新时先合并，再重新核对能力差异；补全内容按功能拆成独立提交，方便逐项审查与取舍。

既定规则：上游发布新功能但不随开源仓库放出对应源码时，本仓库自行补齐等价实现并开源——不等待、不申请、不保留。
