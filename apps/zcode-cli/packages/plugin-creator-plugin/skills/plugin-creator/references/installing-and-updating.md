# Adding, installing, updating and trying a local plugin

Division of labor: the agent prepares the plugin source and the test catalog; the user performs market registration, installation, updates and the trial in the app. None of the steps below needs a global CLI or a Node install.

## The catalog and its root

A local test market is one JSON file:

```text
<workspace>/plugins/
  marketplace.json          name: dev-<label>-<hash>
  my-plugin/
    .zcodium-plugin/plugin.json
    skills/my-plugin/SKILL.md
```

Two locations are legal for the file, and the root is resolved differently for each:

- `<root>/marketplace.json` — the market root is the directory holding the file.
- `<root>/.claude-plugin/marketplace.json` — the market root is the **parent** of `.claude-plugin`.

Every entry's `source` is resolved against that root, which is why the helper writes `./my-plugin` and not a path relative to the file itself. The directory to paste in the UI is always the market root — the one containing `marketplace.json` — never the individual plugin subdirectory.

### The market name

- Catalogs generated by `scripts/upsert-dev-marketplace.mjs` are named `dev-<label>-<hash8>`: the label comes from the root directory name (its parent when the root is itself named `plugins`), the hash from the canonical root path. Re-running the helper in the same workspace keeps the name, so a user never sees the market rename itself.
- A catalog adopted with `--marketplace-path` keeps whatever name it already has. Hand the user that name, not the generated scheme.
- Without `--marketplace-path`, the helper refuses to take over a catalog that is not its own dev market (`Existing marketplace is not this development market; pass --marketplace-path explicitly to reuse it`) — that file may be hand-maintained, and renaming or rewriting its entries would destroy the user's organization.

### What the helper maintains in each entry

| field                    | source                                                          |
| ------------------------ | --------------------------------------------------------------- |
| `name`                   | the plugin manifest name                                        |
| `source`                 | `./<plugin directory>`, recomputed against the market root      |
| `version`                | the manifest `version`, refreshed on every run                  |
| `description`            | the manifest `description`                                      |
| `displayName`            | `--display-name`, else the previous value, else the plugin name |
| `displayName_i18n.zh-CN` | `--name-zh`                                                     |
| `description_i18n.zh-CN` | `--description-zh`                                              |

Everything else in the file — other entries, their order, the market name, any hand-added fields — is preserved verbatim. The helper skips the write entirely when nothing changed, so an unchanged catalog keeps its mtime and the host does not re-read it.

### Three different locations

```text
<workspace>/plugins/my-plugin/   editable source
<workspace>/plugins/marketplace.json   test catalog entry
              |
        user adds the market in the UI
              v
host-managed market  ->  user installs  ->  installed copy
                                              |
                                         new-task trial
```

Creating the catalog does not register a market. Registering does not install. Installing does not prove the capability works.

## First addition and installation

1. In the workspace or host where the files were created, open the plugin store page (**设置 → 插件 / Settings → Plugins**, tab **插件市场 / Marketplaces**).
2. Choose **添加 / Add → 添加插件市场 / Add marketplace**.
3. Paste the actual market root directory from the handoff into the source field, then confirm. The dialog also offers **选择目录 / Choose directory** and file/folder drag-and-drop, but only on Desktop — Web builds hide those entries. For remote work or phone control, paste on the target host: a path that exists only on the phone or on an unrelated machine will not resolve.
4. After the market is added, open **个人 / Personal**, find the actual market name, then the plugin. Check the displayed name, description and expected version in the plugin details before installing.
5. Click **安装 / Install**. The plugin is afterwards also manageable under **设置 → 插件 / Settings → Plugins**. If it arrives disabled or needs configuration, explain the specific manual enable or configuration action and preserve the user's choice.

Existing source files are not a registered market and not an installed plugin. Until the user confirms each step, report addition, installation and trial as pending.

## Trying it

- Give one small acceptance prompt built on the implemented capability, with an observable expected result, and ask the user to run it in a **new task** after installation.
- For a skill, the user selects the installed plugin or skill in the composer picker before sending the prompt. Quote an installed path only when it has actually been observed; a source path is not an installed path.
- For an MCP plugin, describe the expected tool result and any configuration the server needs. For hooks, describe the trigger and the observable effect.
- Old tasks may still carry the previous capability catalog, and a successful installation alone does not prove the capability runs. If the user has not run the example, mark the trial pending; if they report a failure, treat that as the debugging evidence.

## Updating an existing plugin

Agent side:

1. Edit the original source; keep the manifest name and bump `version`.
2. Re-run the validation checks.
3. Re-run `scripts/upsert-dev-marketplace.mjs <plugin-path>`. It refreshes `version` and `description` in the same entry, keeps the market name and plugin identity, and writes nothing when nothing changed.

User side:

1. Open the marketplace page's gear button → **市场源 / Marketplace sources**.
2. Find the actual dev market and click its refresh button (**刷新该市场 / Refresh this marketplace**). Reuse the existing source; do not add the same market twice.
3. Return to **个人 / Personal**, open the plugin details and click **更新 / Update** when it is offered.
4. Confirm the expected version, keep the current enabled/disabled choice, and run the acceptance example in a new task.

Source edits are not hot reload. Refreshing the market updates only the catalog; the installed copy changes only through its own update action. If no update appears, compare the source version, the catalog entry version and the installed version, and confirm the intended market was refreshed on the same host.

## When something fails

| symptom                                                | what to check                                                                                                                                             |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| market add or refresh rejected                         | the pasted root is the directory containing `marketplace.json`; the JSON parses; every `source` resolves inside the root; entry names are unique          |
| `Marketplace is busy: …marketplace.json.lock`          | a previous run crashed; delete the named lock file and retry                                                                                              |
| `Marketplace source conflict: <name>`                  | the catalog already has an entry with that name pointing elsewhere; choose a different plugin name or a different catalog — never rebind the existing one |
| `Plugin directory and manifest name must match`        | the directory name, the manifest `name` and the catalog entry name must be identical                                                                      |
| `A plugin version is required for dev updates`         | the manifest needs a non-empty string `version`                                                                                                           |
| `Existing marketplace is not this development market…` | the sibling catalog was not generated for this dev market; pass `--marketplace-path` to adopt it deliberately                                             |
| placeholder or resource errors from validation         | fix the plugin source first; the catalog update is blocked until the preflight passes                                                                     |

Keep the source files intact while debugging, and never delete or rebind a market automatically. A same-name/different-source conflict is a deliberate choice for the user, not something to resolve by overwriting.

## Handoff message

Always send real values, never placeholders: the absolute source directory, the market root to paste, the catalog file path, the market name, the full plugin ID (`<name>@<market>`), the source version, the trial prompt with its expected result, and the current status — market awaiting manual addition, plugin awaiting installation or update, trial pending — unless completion has actually been observed or reported. Reply in the user's language.
