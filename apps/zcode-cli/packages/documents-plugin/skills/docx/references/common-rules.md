# Common rules

Naming, structure and maintainability — the rules that are not about how a document
looks but about whether it can still be changed in six months. A document that
renders correctly and cannot be edited is a screenshot with extra steps.

## 1. Naming

### 1.1 Files and directories

- The unpacked directory keeps the archive's layout: `[Content_Types].xml`, `_rels/`
  and `word/`. Do not rename a part and do not nest it deeper — every path in this
  plugin is a literal lookup, and `Document.__getitem__` raises
  `ValueError: XML file not found` for a part that moved.
- The output directory is a fresh name (`out/`, `reviewed/`, `revised/`), never the
  input directory. `save()` without a destination copies back over the input, which
  destroys the original.
- The packed archive is named for what it is: `report.docx`, `report-reviewed.docx`.
  `report-final-v2.docx` is a name that stops meaning anything after the next
  revision.

### 1.2 Style ids

- Lower case, hyphenated or camel-cased, and stable: `body-text`, `heading-1`,
  `callout-note`.
- The heading styles are the exception: their ids **must** start with `heading`
  followed by the level, because `heading-continuity` and
  `add_toc_placeholders.py` both read the numeric suffix. `h1` does not work.
- A style id says what the content is, not what it looks like. `red-bold-14pt` is a
  bug report waiting to be filed; `callout-title` is a decision you can revisit.
- One style, one job. A style used for two different things is two styles.

### 1.3 Labels and cross-references

- Prefixed and unique: `fig:`, `tab:`, `eq:`, `sec:`, `clause:`. A bare `label1`
  tells a reader nothing and a search nothing.
- A label goes immediately after a caption, never before it, and never on a bare
  heading line without a suffix — a label on the enclosing paragraph resolves to the
  wrong counter.
- Cross-references resolve the number; they do not restate it. A typed `第 5.2 条`
  in a contract drifts the moment a clause is inserted.

### 1.4 Identifiers the plugin generates

- `w14:paraId`, `w14:textId`, RSIDs, comment ids and change ids are generated by the
  editor and stamped automatically. Never hand-write one: a duplicate `paraId` is
  invalid OOXML and Word refuses the file.
- Comment ids continue after the highest existing `w:id` in `word/comments.xml`. Do
  not renumber existing comments to make a new one start at zero.

## 2. Structure

### 2.1 One owner per decision

- The style owns typography. A paragraph that overrides its style is a second owner
  of the same decision, and the two will disagree later.
- The section owns page geometry and page numbering. A page break in the middle of
  what should be a section change is the most common structural defect in a document
  built by hand.
- The numbering definition owns list numbering. A typed number is a second owner.

### 2.2 The hierarchy is real

- Heading levels are used in order, with no skipping. A jump from H1 to H3 breaks the
  outline, the table of contents, and the gate.
- A heading is a paragraph with a heading style. A run made large and bold by hand is
  not a heading, whatever it looks like.
- Sections change numbering; page breaks change pages. A document that restarts page
  numbering mid-way with a page break instead of a section break cannot be fixed
  without rebuilding it.

### 2.3 One numbering sequence per purpose

- A numbered list, a clause list and a question list each have their own numbering
  definition, each restarting where it should.
- The `numId` values in use must be contiguous integers. Gaps come from copying
  content between documents; `numbering-continuity` reports them.

### 2.4 Content is not layout

- Spacing between paragraphs is a paragraph property, not an empty paragraph.
- A rule is a border, not a run of underscores or hyphens.
- A box is a bordered paragraph or a single-cell table, not four empty paragraphs
  with borders.
- An indent is `w:ind`, not leading spaces or tabs typed into the text.

## 3. Maintainability

### 3.1 Idempotence

Every operation this plugin performs is safe to run twice, and that is a property to
preserve in your own workflow:

| operation                 | second run                                                                        |
| ------------------------- | --------------------------------------------------------------------------------- |
| `Document(...)`           | idempotent; settings elements already present are left alone                      |
| `save()`                  | adds relationships and content types only when missing                            |
| `fix_footer_fields.py`    | matches only the bare keyword; a footer with a switch is untouched                |
| `add_toc_placeholders.py` | clears then rewrites, so the document serialises back to itself; `written: False` |
| `postcheck.py`            | read-only, always                                                                 |

If you add a step to a workflow, make it idempotent too. A repair script that
appends is a script that can only be run once.

### 3.2 Keep the source

- The unpacked tree is the editable form. Keep it next to the output, or keep the
  build path that produced the output, because a `.docx` whose source has been
  thrown away cannot be revised — only patched.
- Data files a chart was built from live next to the document, not embedded in it.
- Never hand-patch a packed `.docx`. Unpack, edit through the API, repack. A
  hand-patched archive diverges from its source on the next build.

### 3.3 Run the gate at the end, not in the middle

- Comments and tracked changes rewrite the XML the gate reads, so the gate runs after
  the edits are saved and packed.
- `add_toc_placeholders.py` re-serialises `word/document.xml` through ElementTree, so
  run it after any edit that depends on the part's exact byte layout.
- The order that works: build → edit → repair scripts → `postcheck.py`.

### 3.4 Record what was scoped

- `cover-separation` fails a single-section document by design. When you scope the
  run with `--only`, record why in the change that produced the document — otherwise
  the next person cannot tell a deliberate scope from an ignored failure.
- A rule that reports a failure you have decided is acceptable is still a failure.
  Write the decision down.

### 3.5 No invented capability

- This plugin has no generator, no renderer, no converter and no schema validator.
  `validate()` is a presence check.
- Do not describe a capability the code does not have, and do not add a workaround
  branch to paper over a missing one. A document that needs a renderer needs a
  different tool, not a bigger plugin.

## 4. Cross-platform notes

- Paths: use the platform's separator through a path library, never a literal `/` or
  `\` in a document's own content.
- Fonts: a face available on the build machine is not available on the reader's.
  That is what `font-fallback` is for, and it applies to Windows, macOS and Linux
  alike.
- Line endings and encodings: `XMLEditor` detects the encoding from the part's
  header and `save()` preserves it. Do not rewrite a part with a different encoding.
- The scripts run on any Python 3.10+ with `defusedxml`; nothing here is
  platform-specific.

## 5. The short version

1. Name things for what they are, not for how they look.
2. Let the style own typography, the section own the page, the numbering definition
   own the list.
3. Spacing is a property; a rule is a border; an indent is an attribute.
4. Every step is safe to run twice.
5. Keep the source next to the output.
6. Gate last, and record every scope.
